选择开发板时，参数表只能回答一部分问题。更实用的起点是：设备要连接什么、长期保存什么、谁来使用、出现故障后如何恢复？Sige5 与 Sige7 提供完整单板形态，结合 Armbian，可以从一个小服务逐步建立自己的 Linux 应用环境。

本文给出六种项目方案及验收方法，均为开发设计建议，不是已经跑通的软件清单或性能测试。镜像中的具体驱动与应用版本必须独立核对。

## 1. 两块板，先看接口需求

| 平台 | 选型锚点 | 适合优先评估的方向 |
|---|---|---|
| Sige5 | RK3576、双千兆网络、NVMe扩展 | 数据采集、设备服务、日常Linux开发 |
| Sige7 | RK3588、双2.5GbE、PCIe 3.0存储扩展 | 多服务主机、较高带宽的存储原型 |

以上是硬件特征，不是 Armbian 下的吞吐量保证。实际能力由存储、散热、软件栈和对端共同决定。详细配置见 [Sige5 产品页](https://www.armsom.org/sige5) 与 [Sige7 产品页](https://www.armsom.org/sige7)。购买前按所选版本核对内存、存储和附件。

Armbian 分别提供 [Sige5](https://armbian.com/boards/armsom-sige5) 与 [Sige7](https://armbian.com/boards/armsom-sige7) 页面。不要因为两块板的外形相近就交换镜像。当前条目属于社区支持；镜像选择与首次启动参见本系列入门篇。

## 2. 方案一：随手可用的 Linux 开发桌面

把编辑器、终端、Git工作目录和串口工具放在一块板上，可以减少在多台设备之间搬运项目的步骤。适合教学实验、编译小工具、调试网络接口，以及作为专用开发终端。

先用一个屏幕和键鼠验证登录、显示模式、音频与网络，再运行实际编辑器。确认软件有适合目标架构的包；桌面能够显示，不代表浏览器视频、3D或所有图形API已经硬件加速。验收以具体任务为准：编辑一个项目、完成一次构建、连接一块外部设备、重新登录后恢复工作。

## 3. 方案二：局域网容器服务主机

一个小型仪表盘、项目文档站或消息服务，可以帮助理解服务部署。先运行一个应用，再决定是否采用容器。容器能够隔离依赖，但不能替代宿主机内核驱动；镜像必须有适合目标CPU架构的版本。

把应用数据目录与容器生命周期分开，设置日志轮转、资源限制与健康检查。只开放必要端口，先局域网测试；不要把管理面板直接暴露到公网。验收需要包含设备重启、服务异常退出、存储变满以及从备份恢复。能够重新创建容器却找不回数据，仍不算完成部署。

## 4. 方案三：个人文件库与备份节点

从家庭照片、项目归档或小团队文件共享入手，比一开始追求峰值带宽更容易验证价值。先确认磁盘识别和挂载路径，再选择文件服务。采用稳定的磁盘标识，避免盘符变化导致服务写到错误位置。

区分系统盘、应用数据和备份副本。网络共享不等于备份，多块盘也不能代替异地或离线副本。测试大文件、许多小文件、两台客户端并发和断电恢复后的文件完整性。Sige7的网络与存储接口可作为选型因素，但不能直接按接口标称速率计算实际传输成绩。

## 5. 方案四：自动化与物联网控制台

让板卡汇总传感器数据、显示状态、转发消息，是一个可逐步扩展的方向。可以把系统拆成采集、消息、规则和展示四个服务，先用模拟数据贯通流程，再接真实设备。

GPIO、I2C和串口需核对引脚、电平、复用和驱动。UART不是RS485，现场总线通常还需要收发器与隔离。外接USB无线协调器也要确认芯片及驱动。验收重点是断网时是否安全、恢复后是否重复执行命令，以及时间不同步时能否识别过期数据。

## 6. 方案五：网络与运维学习实验台

双网口便于建立隔离的实验网络，学习路由、服务监测和远程维护。先保留一条独立管理通道，记录接口名称，再逐步修改网络配置。操作错误时，应能通过本地控制台恢复。

下面是非破坏性的基础检查；并非自动开启路由或配置防火墙。

```sh
ip -br link
ip route
ss -lnt
lsblk -o NAME,SIZE,TYPE,MOUNTPOINTS
df -h
```

不要把实验配置直接复制到办公网络。验收应包括地址冲突、链路断开、重启后配置持久化和管理权限，而不仅是“能上网”。

## 7. 方案六：边缘视觉应用原型

可以把图像采集、预处理、推理和结果展示拆开开发。先从图片文件建立准确性基线，再接摄像头；先让结果可重复，再追求帧率。这样可以知道瓶颈来自采集、模型还是显示。

芯片具有NPU并不意味着安装 Armbian 后应用会自动使用它。需要匹配的内核驱动、RKNN运行库、模型转换版本和应用接口。摄像头、ISP、视频编解码也各有支持条件。记录端到端延迟、准确性、CPU占用、温度与长时间丢帧，不以TOPS替代应用实测。若依赖尚未打通，保留CPU参考实现有助于排查。

## 8. 为项目建立验收表

| 阶段 | 留下的证据 |
|---|---|
| 基础启动 | 板卡版本、镜像名、内核与供电记录 |
| 功能验证 | 真实输入、预期输出、失败与恢复步骤 |
| 长时间运行 | 内存趋势、日志增长、温度与错误记录 |
| 更新维护 | 备份恢复、更新前后对比、回退方法 |

先选一个方案做到可恢复，再组合多个服务。桌面加文件服务、采集加消息服务，都要重新验证资源竞争，而不是简单相加。ArmSoM的板级资料与Armbian的构建入口提供起点，项目最终可用性由你的应用验证决定。
