### 3.1.6 Интерфейс нулевого копирования RKNN Runtime

#### 3.1.6.1 Введение в нулевое копирование

RK3562 / RK3566 / RK3568 / RK3576 / RK3588 / RV1126B предоставляют общий API и API нулевого копирования; серии RV1103 / RV1106 поддерживают API нулевого копирования. Примеры находятся в examples/rknn_zero_copy проекта rknpu2. Репозиторий и дополнительные сведения: https://github.com/airockchip/rknn-toolkit2/tree/master/rknpu2.

При инференсе RKNN исходные данные проходят обработку входа, выполнение модели NPU и обработку выхода. В зависимости от входного формата и квантования интерфейсы реализуют два процесса: общий API и нулевое копирование, показанные на рисунках 3-5 и 3-6. Главное различие состоит в том, что при каждом обновлении кадра общий интерфейс копирует данные внешнего модуля во входную память NPU Runtime, а интерфейс нулевого копирования непосредственно использует заранее выделенную память — самим Runtime либо внешним фреймворком, например DRM. Это сокращает копирование, повышает производительность и уменьшает расход пропускной способности. Если входные данные имеют только виртуальный адрес, доступен лишь общий API; при физическом адресе или fd доступны оба. Смешивать вызовы двух групп API нельзя.

Рисунок 3-6. Обработка данных API нулевого копирования

1 Обычный API

В общем API, показанном на рисунке 3-5, нормализация, квантование, преобразование размещения и деквантование выполняются на CPU, а модель — на NPU. Если соблюдены требования входа нулевого копирования, нормализация и квантование выполняются на NPU, но CPU всё равно копирует входные данные в буфер модели.

1 API нулевого копирования

Нулевое копирование на рисунке 3-6 оптимизирует общий процесс: нормализация, квантование и инференс выполняются на NPU, а преобразование размещения выхода и деквантование — на CPU или NPU. Обработка входного потока эффективнее общего API.

Условия использования нулевого копирования приведены в таблице:

#### 3.1.6.2 Процесс нулевого копирования C API

API нулевого копирования использует структуру rknn_tensor_memory, создаваемую и настраиваемую до инференса; после него читаются данные соответствующей памяти. В зависимости от самостоятельного выделения памяти входов, выходов, весов и промежуточных результатов, а также её представления через fd или физический адрес, существуют три типичных процесса на рисунках 3-7–3-9. Красным выделены добавленные для нулевого копирования интерфейсы и структуры, курсивом — структуры, передаваемые между вызовами.

Входная и выходная память выделяется Runtime

Рисунок 3-7. Вызовы API нулевого копирования: внутреннее выделение входной и выходной памяти

#### 3.1.6.3 Использование C API нулевого копирования

Рассмотрим использование на примере рисунка 3-7 с внутренним выделением памяти входов и выходов:

rknn_query()

Вход:

Запрашивайте атрибуты через RKNN_QUERY_NATIVE_INPUT_ATTR, не RKNN_QUERY_INPUT_ATTR. Требуемая предобработка зависит от полученного fmt (layout). Такой запрос возвращает наиболее эффективные для аппаратуры тип и размещение входа.

Варианты входа rknn_query():

a. RKNN_TENSOR_NCHW: обычно четырёхмерный вход bool или int64. Данные NPU также должны быть организованы в NCHW.

b. RKNN_TENSOR_NHWC: обычно четырёхмерный вход float32/float16/int8/uint8 с 1, 3 или 4 каналами. Данные передаются в NHWC. При pass_through=1 ширину может потребоваться выровнять по stride согласно запрошенному w_stride.

c. RKNN_TENSOR_NC1HWC2: обычно четырёхмерный вход float16/int8, число каналов не равно 1, 3 или 4. При pass_through=0 вход организуется в NHWC, а интерфейс преобразует его на CPU в NC1HWC2. При pass_through=1 требуется NC1HWC2, и пользователь выполняет преобразование самостоятельно.

d. RKNN_TENSOR_UNDEFINED: обычно вход не четырёхмерный. Данные передаются в формате входа модели ONNX. NPU не выполняет обработку mean/std и преобразование размещения.

Если нужна конфигурация входа, отличная от полученной rknn_tensor_attr, структуру можно изменить. Допустимые изменения типов приведены в таблице 3-3. Особенно важно: если запрошен uint8, а передавать нужно float32, размер в rknn_tensor_attr увеличивается в четыре раза, тип меняется на RKNN_TENSOR_FLOAT32. После изменения эффективность аппаратуры уже не оптимальна: интерфейс выполняет преобразование типа на CPU.

Таблица 3-3. Допустимые изменения типа входа

| Тип пользователя / тип модели | bool | int8 | float16 | int16 | int32 | Int64 |
| --- | --- | --- | --- | --- | --- | --- |
| bool | Y |  |  |  |  |  |
| int8 |  | Y |  |  |  |  |
| uint8 |  | Y | Y |  |  |  |
| float32 |  | Y | Y |  |  |  |
| float16 |  |  | Y |  |  |  |
| int16 |  |  |  | Y |  |  |
| int32 |  |  |  |  | Y |  |
| Int64 |  |  |  |  |  | Y |

Выход:

Запрашивайте атрибуты через RKNN_QUERY_NATIVE_OUTPUT_ATTR, не RKNN_QUERY_OUTPUT_ATTR. Требуемая постобработка зависит от fmt (layout). Запрос возвращает наиболее эффективные для аппаратуры размещение и тип выхода.

Если четырёхмерный выход нужен в NHWC, используйте RKNN_QUERY_NATIVE_NHWC_OUTPUT_ATTR: так выход NHWC можно получить напрямую.

Варианты выхода rknn_query():

a. RKNN_TENSOR_NC1HWC2: обычно четырёхмерный выход float16/int8. Для NCHW пользователь должен выполнить внешнее преобразование NC1HWC2 → NCHW.

b. RKNN_TENSOR_UNDEFINED: обычно выход не четырёхмерный, тип float16/int8. Внешнее преобразование размещения не требуется.

c. RKNN_TENSOR_NCHW: обычно четырёхмерный выход float16/int8. Внешнее преобразование размещения не требуется.

d. RKNN_TENSOR_NHWC: обычно четырёхмерный выход float16/int8. Такой результат обычно получается при запросе через RKNN_QUERY_NATIVE_NHWC_OUTPUT_ATTR.

Если требуемая конфигурация выхода отличается от rknn_tensor_attr, структуру можно изменить согласно таблицам 3-5 и 3-4. Особенно важно: при запрошенном int8 и требуемом float32 размер увеличивается в четыре раза, тип меняется на RKNN_TENSOR_FLOAT32. После этого аппаратная эффективность уже не оптимальна: преобразование выполняет CPU внутри интерфейса.

rknn_create_mem

Структуру rknn_tensor_memory создают и настраивают до инференса, а затем читают память результатов. Если тип и размещение, запрошенные через RKNN_QUERY_NATIVE_INPUT_ATTR и RKNN_QUERY_NATIVE_OUTPUT_ATTR, не изменяются, выделяйте память размера size_with_stride. При изменении типа или размещения нужен соответствующий размер: например, при переходе выхода int8 → float32 он увеличивается в четыре раза.

rknn_set_io_mem

rknn_set_io_mem() задаёт структуру rknn_tensor_mem с информацией о входной и выходной памяти модели. Как и rknn_init(), её достаточно вызвать один раз в начале, после чего rknn_run() можно выполнять многократно.
