# Полное руководство Rockchip Secure Boot: подпись, eFuse, OTP и проверка

Полный перевод английского RK-SM-YF-024 V2.2.0 с техническим предисловием стр. 2–3 и всем техническим содержанием стр. 8–43. Есть только английский PDF; рисунки всех языков взяты из него, некоторые интерфейсы инструментов в нём китайские. Поддержка ограничена чипами источника, не расширяется на новые SoC или все платы ArmSoM. Проверьте SDK/BSP, Loader/U-Boot, ROM, формат ключей, напряжение программирования и питание платы. Проверка ArmSoM, подпись, прошивка и запись предохранителей не выполнялись.

> Программирование eFuse/OTP необратимо; неверные ключи или напряжение могут лишить устройство загрузки и обновлений. Это эталонные процедуры производителя, не готовый рецепт для платы. Сохранены и отмечены противоречия: rsaHash[128] и RSA2048 в §2.5; RK3336 в §7.5 и RK3326 в §7.6; старые ссылки разделов; термины RSA Encryption/Decryption. Значения не исправлены догадками.

[ArmSoM Docs](https://docs.armsom.org/) · [Rockchip U-Boot](https://github.com/rockchip-linux/u-boot)

## 1. Предисловие

Термины (определения источника):

| Термин | Определение |
| --- | --- |
| Sector | Размер сектора 512 байт |
| eFuse | IP однократно программируемой памяти в SoC |
| RSA Encryption | Шифрование открытым ключом |
| RSA Decryption | Расшифрование закрытым ключом |
| OTP | IP однократно программируемой памяти в SoC |
| MaskRom | BootROM, загрузочная память только для чтения в SoC |
| loader | Загрузчик/первый загрузчик, обычно RKMiniloader или SPL(uboot) |
| OBM CODE | Обычно код, собранный или доверенный OEM/OBM |

Документ описывает реализацию безопасной загрузки Rockchip. Проверка действительности прошивки предотвращает недопустимые обновления и загрузку. После программирования eFuse устройство включает secure boot ROM и не загружает неподписанную прошивку; обновление неподписанной прошивкой или подписью другого ключа завершается ошибкой.

Примечание: корректно подписанная прошивка может запускаться на копиях платы или аппаратуре той же CPU-платформы. Secure boot проверяет программное обеспечение, а не аппаратуру.

Область источника: RK3126, RK3128, RK3228, RK3229, RK3288, RK3368, RK3399, RK3228H, RK3328, RK3326, RK3308 и PX30. Возможности: secure boot ROM, SHA256, RSA2048, проверка открытого ключа хешем eFuse/OTP.

Версии инструментов по источнику: Efuse tool V1.35 или новее; SecureBootTool 1.79 или новее; RKBatchTool 1.8 или новее (устарел, заменён FactoryTool); FactoryTool 1.39 или новее. Это исторические требования документа; §7.6 отдельно требует SecureBootTool V1.9 или новее.

Рисунок 1-3-1: последовательность MaskRom → loader. Размещение первого загрузчика в пользовательском разделе flash. Таблица 1-1: структура данных первого загрузчика.

| Range | Описание |
| --- | --- |
| 0–63 sector | 64 sector reverse (оригинал) |
| Первый загрузчик (8128 sector)(5 копий) | Раздел загрузчика |
| 0-2047 | Заголовок загрузчика |
| 2048-4095 | Открытый ключ и цифровая подпись |
| 4096 - | Исходный бинарный файл |
| ... |  |
| Раздел копии загрузчика (4) |  |
| 0-2047 | Заголовок загрузчика |
| 2048-4095 | Открытый ключ и цифровая подпись |
| 4096 - | Исходный бинарный файл |

Структура открытого ключа и цифровой подписи по адресам 2048–4095:

```c
typedef struct tagBOOT_HEADER
{
    uint32 tag;
    uint32 version;
    uint32 flags;
    uint32 size;
    uint32 reserved1[3];
    uint16 HashBits;
    uint16 RSABits;        /* length in bits of modulus */
    uint32 RSA_N[64];      /* RSA public key*/
    uint32 RSA_E[64];
    uint32 RSA_C[64];
    uint32 HashData[(8+1)*2];
    uint32 signature[64];
}BOOT_HEADER, *PBOOT_HEADER;
```

Открытый ключ: `uint32 RSA_N[64], RSA_E[64], RSA_C[64];` Цифровая подпись: `uint32 signature[64]`. Шаг 1: получите открытый ключ из раздела первого загрузчика. Шаг 2: вычислите SHA256 ключа и сравните с хешем в OTP; при совпадении первый загрузчик успешно загружается, иначе загрузка неуспешна. Шаг 3: вычислите SHA256 исходного бинарного файла и сравните с результатом RSA2048-шифрования подписи с открытым ключом шага 1; совпадение означает успешную загрузку первого загрузчика, иначе отказ. Формулировки шагов 2 и 3 сохранены из источника.

Таблица 1-4: размещение U-Boot во flash. Структура заголовка с цифровой подписью по адресам 0–2047:

```c
typedef struct tag_second_loader_hdr
{
    unsigned char magic[LOADER_MAGIC_SIZE];
    unsigned int version;
    unsigned int reserved0;
    unsigned int loader_load_addr;         /* load to DDR address */
    unsigned int loader_load_size;         /* size in bytes */
    unsigned int crc32;                    /* crc32 */
    unsigned int hash_len;                 /* 20 or 32 , 0 is no hash */
    unsigned char hash[LOADER_HASH_SIZE];  /* sha256 */
    unsigned int js_hash;                  /* js hsah */
    unsigned char reserved[1024-32-32-4];
    unsigned int signTag;                  /* 0x4E474953, "NGIS" */
    unsigned int signlen;                  /* 256 */
    unsigned char rsaHash[256];            /* digital signature */
    unsigned char reserved2[2048-1024-256-8];
}second_loader_hdr;
```

Цифровая подпись: `unsigned char rsaHash[256];` Шаг 1: получите открытый ключ из первого загрузчика. Шаг 2: сравните SHA256 ключа с хешем OTP; при совпадении продолжите, иначе отказ загрузки. Шаг 3: сравните SHA256 исходного бинарного файла с RSA2048-шифрованием подписи с ключом шага 1; при совпадении загрузка успешна и ключ передаётся U-Boot, иначе отказ.

Структура заголовка по адресам 0–2047:

```c
#define BOOT_MAGIC_SIZE 8
#define BOOT_NAME_SIZE 16
#define BOOT_ARGS_SIZE 512
typedef struct tag_boot_img_hdr
{
    unsigned char magic[BOOT_MAGIC_SIZE]; /* "ANDROID!" */
    unsigned int kernel_size;             /* size in bytes */
    unsigned int kernel_addr;             /* physical load addr */
    unsigned int ramdisk_size;            /* size in bytes */
    unsigned int ramdisk_addr;            /* physical load addr */
    unsigned int second_size;             /* size in bytes */
    unsigned int second_addr;             /* physical load addr */
    unsigned int tags_addr;               /* physical addr for kernel tags */
    unsigned int page_size;               /* flash page size we assume */
    unsigned int unused[2];               /* future expansion: should be 0 */
    unsigned char name[BOOT_NAME_SIZE];   /* asciiz product name */
    unsigned char cmdline[BOOT_ARGS_SIZE];
    unsigned int id[8];                   /* timestamp / checksum / sha1 / etc */
    unsigned char reserved[0x400-0x260];
    unsigned int signTag;                 /* 0x4E474953 */
    unsigned int signlen;                 /* 128 */
    unsigned char rsaHash[128];
}boot_img_hdr;
```

Цифровая подпись: `unsigned char rsaHash[128];` Шаг 1: U-Boot получает открытый ключ первого загрузчика. Шаг 2: сравните SHA256 ключа с OTP; при совпадении продолжите, иначе отказ. Шаг 3: сравните SHA256 исходного бинарного файла с RSA2048-шифрованием подписи с ключом шага 1; при совпадении запустите ядро Linux, иначе отказ.

## 3. Разметка eFuse

RK3368, RK3288, RK3229 и RK3228 используют eFuse 1024 bit для безопасной загрузки. Таблица 2-1: размещение данных eFuse.

| 32-битная адресация словами | Описание |
| --- | --- |
| 0x00 | Флаг безопасности Bits[7:0]: включение; Bits[31:8]: резерв |
| 0x01-0x3 | Зарезервировано |
| 0x04-0x07 | Зарезервировано |
| 0x8-0xF | Хеш открытого ключа RSA |
| 0x10-0x17 | Зарезервировано |
| 0x18 | Зарезервировано |
| 0x19-0x1A | Зарезервировано |
| 0x1B-0x1D | Зарезервировано |
| 0x1E | Зарезервировано |
| 0x1F | Биты блокировки записи eFuse |

RK3228H и RK3328 используют OTP 7680 bit для безопасной загрузки. Таблица 2-2: размещение OTP.

| 32-битная адресация словами | Описание |
| --- | --- |
| 0-63 | Открытый ключ (N) |
| 64-127 | Открытый ключ (E) |
| 128 | Bits[7:0]: 0xff — включение; Bits[15:8]: размер RSA_E (в источнике word uint); Bits[31:16]: резерв |
| 129 | Счётчик отзыва доверенной прошивки (ID #0) |
| 130-131 | Счётчик отзыва недоверенной прошивки (ID #1) |
| 132-239 | Зарезервировано |

RK3326, PX30 и RK3308 используют OTP 4096 bit для безопасной загрузки. Таблица 2-3: размещение OTP 2.

| 32-битная адресация словами | Описание |
| --- | --- |
| 0 | Флаг включения безопасной загрузки |
| 1-3 | Зарезервировано |
| 4-11 | Хеш открытого ключа RSA (SHA256) |
| 12-19 | Корневой ключ устройства |
| 20-23 | Ключ шифрования прошивки |
| 24-25 | Счётчик отзыва доверенной прошивки (ID #0) |
| 26-31 | Счётчик отзыва недоверенной прошивки (ID #1) |
| 32-97 | Резерв для OEM |

## 7. Программирование eFuse

### 7.1 Аппаратные условия

Для Rockchip AP есть два способа записи пользовательских защищённых данных: eFuse и OTP, поддерживаемый лишь некоторыми чипами. Описание ниже.

#### 7.1.1 Программирование eFuse

RK3126, RK3128, RK3228, RK3229, RK3288, RK3368 и RK3399 поддерживают программирование eFuse. Общие требования:

A. Если программирование не нужно, рекомендуется напрямую заземлить питание eFuse во избежание случайного изменения данных. У RK3126/RK3126C этот вывод совмещён с SARADC, поэтому заземлять его нельзя.

B. Если программирование нужно, подключите подтягивающий к земле резистор к питанию eFuse, чтобы напряжение не колебалось в обычном режиме и исключалось случайное программирование. Номинал берётся из схемы платформы, обычно 47Ω–10KΩ.

C. Есть два способа питания. a) Питание на основной плате: не нужна PCBA-плата с контактной оснасткой; можно сначала запрограммировать eFuse, затем обновить прошивку. В обычном режиме прошивка должна отключать питание eFuse, удерживая 0V. Недостатки: схема питания занимает плату, увеличивает стоимость компонентов и требует гарантии отсутствия ошибочных действий прошивки. Подходит продуктам без дополнительного PCBA-тестирования, например некоторым BOX с простыми интерфейсами и сборкой, где контактная оснастка не нужна. b) Питание от PCBA-тестовой платы (рекомендация источника): на основной плате нужны лишь тестовые точки, без схемы питания; пользователь не может взломать этот путь питания программно. Недостатки: добавляются этап PCBA-теста и его стоимость. Подходит сложным изделиям, например планшетам, где ремонт и замена дефектной PCBA после сборки трудны и тестирование обычно уже существует; программировать eFuse на этом этапе разумно.

D. Напряжения eFuse различаются по платформам (например 1.5/1.8/2.5V), как и номера выводов и требования по току.

### 7.6 Программирование OTP

### 9.2 Тест безопасной загрузки

## 10. Защищённая отладка

### 10.1 Введение

Secure Debug лишь отключает проверку безопасной загрузки для обновления неподписанного ядра и ускорения отладки. Каждый SoC имеет уникальный 128-битный CPU ID. Инструмент читает ID и выполняет названную источником Decryption операцию закрытым RSA-ключом, создавая сертификат. Устройство проверяет его открытым RSA-ключом; после успеха U-Boot отключает проверку загрузки. Это контролируемый процесс производителя, не разрешение обходить авторизацию чужих устройств.
