# Полное руководство Rockchip PCIe EP: Chips Connect, DMA, память и приёмка

Оригинал V3.2.0: 44 страницы на китайском, 46 на английском. Версии: RK3588 Linux 6.1/5.10, RT-Thread v5.1.x/v4.1.x; RK3568 Linux 6.1/5.10/4.19, RT-Thread v5.1.x/v4.1.x; RK1820 RT-Thread 5.1.x. ## 1. Обзор карты EP

Комплект разработки стандартной карты RK PCIe EP объединяет аппаратные и программные материалы для изделий в форм-факторе карты RK PCIe EP. Он основан на демонстрационной плате RK EP (далее — карта EP) и включает:

- краткое руководство по работе с картой EP;
- схемы загрузки, разработку аппаратной и программной части PCIe и обновление OTA;
- основы прикладной обработки на карте EP;
- примеры приложений на этой основе.

## 2. Характеристики карты EP

### 2.1 Основные характеристики

| Основная микросхема | Схема загрузки | Расширение SMBus | Независимое тактирование |
| --- | --- | --- | --- |
| RK3568 | Поддерживает Flash Boot, Common Boot; не поддерживает PCIe Boot | N | Поддерживает SRNS; не поддерживает SRIS |
| RK3588 | Поддерживает Flash Boot, Common Boot; не поддерживает PCIe Boot | N | N |
| RK1820 | Поддерживает Flash Boot, Common Boot, EP Boot | Y | N |

Пояснение. Flash Boot включает две схемы:

- Flash Boot с интеграцией PCIe Bin и программной схемы EP Boot;
- Flash Boot с интеграцией PCIe Bin.

Для схем EP, не поддерживающих PCIe Boot, протокол PCIe требует перехода карты EP в режим обнаружения в течение 20 ms после снятия PERST#. Затем RC выполняет непрерывное обнаружение, согласование и перечисление; этот процесс может занимать до 100 ms. Поэтому для совместимости с универсальным RC рекомендуется использовать SPI Flash как загрузочный носитель, обеспечивающий быстрый запуск; обычно рекомендуется SPI NOR.

### 2.2 Разработка программного обеспечения

Комплект EP предназначен для демонстрации функций изделия PCIe, а не представляет собой готовое комплексное решение. Заказчик должен самостоятельно доработать PCIe и приложения верхнего уровня на его основе.

### 2.3 Операционные системы

Устройства EP: карта совместима с Linux, Android и RT-Thread.

Устройства RC:

- Совместимость с Linux проверена на определённых RC.
- Совместимость с Windows проверена на определённых RC, однако реализованы только базовые функции передачи. Остальные функции заказчик должен разработать самостоятельно, ориентируясь на драйвер Linux.

### 2.4 Требования к тактированию

Рекомендуется использовать общий опорный тактовый сигнал: EP получает опорную частоту 100M от RC. Если обе стороны используют микросхемы RK и карта EP поддерживает независимое тактирование, RC и EP могут использовать внутренние частоты 100M. Это позволяет отказаться от внешнего генератора и буфера тактового сигнала.

### 2.5 Идентификатор устройства PCI

По умолчанию карта RK PCIe EP использует идентификатор устройства, определённый RK. Для сторонних разработчиков действуют следующие требования исходного документа:

- При использовании устройства исключительно в закрытой внутренней среде можно использовать существующий VID RK PCIe.
- Для продажи или публичного использования устройства необходимо самостоятельно получить VID в PCI-SIG.

### 2.6 Горячее подключение

Карта RK PCIe EP не поддерживает горячее подключение.

### 2.7 Вспомогательные сигналы

| Вспомогательный сигнал | Функция | Стандартная схема EP | Соединение RK с независимым питанием |
| --- | --- | --- | --- |
| PRSNT# | N |  |  |
| PERST# | Вход GPIO | Обязательно; системный сброс всей платы | Обязательно; вход GPIO, программный сброс, DTS reset-gpios; |
| CLKREQ# | Вход FUNCTION | Необязательно; для расширения управления питанием ASPM L1SS. Ещё не реализовано, но рекомендуется резервировать; при отсутствии потребности можно не подключать | Необязательно; для расширения управления питанием ASPM L1SS. Ещё не реализовано, но рекомендуется резервировать; при отсутствии потребности можно не подключать |
| JTAG | N |  |  |
| SMBus | N |  |  |
| WAKE# | Выход GPIO | Обязательно; расширение пробуждения из сна, ещё не реализовано, рекомендуется резервировать | Обязательно; пробуждение, DTS wake-gpios; |
| +3.3Vaux | N |  |  |

Пояснения:

- При независимом питании соединённых микросхем RK одна сторона может потерять питание, пока другая продолжает выдавать сигналы. Рекомендуется защита IO от подачи напряжения/тока в обесточенную сторону.
- Контакты, используемые как GPIO, не следует настраивать в pinctrl как PCIe. Допускаются произвольные GPIO. Для сигналов FUNCTION выбирают соответствующие функциональные контакты.
- В стандартной схеме PERST# подключают к системному сбросу всей платы. Это крайнее средство физического сброса EP со стороны RC. Некоторые RC сразу после перечисления переходят в L2 и сбрасывают PERST#, что требует быстрого сброса.
- PERST на RC имеет сильный двухтактный выход PP, а контакт PMIC на EP — открытый сток OD. Независимо от уровня PERST 3.3V или 1.8V, RESET_L на EP необходимо управлять через согласующую схему.

### 2.8 Требования к производительности

Необходимо определить требуемую полосу передачи PCIe, направление потока данных (односторонняя передача RC/EP или двусторонняя), наличие мелких управляющих сообщений и больших блоков данных. Рекомендуется:

- изучить раздел измеренной производительности, чтобы понять верхний предел производительности комплекта chips_connect;
- изучить раздел «Производительность: пользовательский пример pcie_speed_test», чтобы оценить полосу передачи при разных размерах блоков.

## 3. Руководство по работе с картой EP

### 3.1 Подготовка среды

Карта EP поддерживает подключение к универсальному RC и к RK RC. Здесь кратко описана базовая функциональная проверка обоих вариантов.

#### 3.1.1 Аппаратная среда

Стандартная плата RK3588 EP с RK3588 RC:

- RC: RK3588-EVB1-V10. Подключите питание, последовательный кабель, кабель загрузки прошивки USB–Type-C и HDMI к HDMI_OUT0.
- EP: RK3588-EVB4-V11. Питание подаётся непосредственно RC; отдельный кабель не нужен. Горячее подключение не поддерживается: соедините платы до включения RC.

Стандартная плата RK3588 EP с универсальным RC:

- RC: PC.
- EP: RK3588-EVB4-V11. Питание подаётся RC; отдельный кабель не нужен. Подключите карту до включения RC.

Соединение RK3588 с независимым питанием:

- RC: RK3588-EVB1-V10. Подключите питание, последовательный кабель, USB–Type-C для загрузки прошивки и HDMI_OUT0.
- EP: RK3588-EVB4-V12. Плата питается отдельно; R8114 и R2005 не устанавливаются.

Обязательно соедините PERST# и WAKE#, используя их как GPIO. Подключите питание, последовательный кабель и USB–Type-C для загрузки прошивки.

#### 3.1.2 Программная среда

Необходимые loader, uboot, boot и файловая система находятся в каталоге images поставляемого пакета.

Flash Boot с интеграцией PCIe Bin: загрузочные файлы для платы RK3588 EP приведены ниже.

| Элемент | Имя файла | Описание |
| --- | --- | --- |
| RC (для универсального RC не требуется) | rk3588-update-rc-evb7-v11.img | Запись во Flash RC |
| EP | rk3588-update-ep-evb4-v11.img | Запись во Flash EP |

Примечание: update.img включает MiniLoaderAll.bin, uboot.img, boot.img, rootfs.img и другие файлы.

Flash Boot с интеграцией PCIe Bin и EP Boot: загрузочные файлы для RK3588 EP приведены ниже.

| Элемент | Имя файла | Описание |
| --- | --- | --- |
| RC (для универсального RC не требуется) | rk3588-update-rc-evb7-v11.img | Запись во Flash RC |
| EP | RK3588_MiniLoaderAll.bin | Запись во Flash EP |
| EP | pcie_idb.img | Запись во Flash EP |
| EP | normal_idb.img | Запись во Flash EP |
| EP | uboot.img | RC загружает в DDR EP по PCIe |
| EP | boot.img (содержит kernel+rootfs) | RC загружает в DDR EP по PCIe |

Загрузку прошивки с RC на EP по PCIe см. в следующем разделе функциональной проверки.

### 3.2 Функциональная проверка

Примеры проверки PCIe EP находятся в каталоге examples SDK. Они включают программы EP и RC, а также инкапсулированный код обмена сообщениями и данными.

#### 3.2.1 Linux RC

Файлы bin и ресурсы для универсального RC находятся в images и копируются на RC вручную (только X86). Ресурсы RK RC уже входят в корневой каталог прошивки. После подготовки аппаратной и программной среды выполните следующие шаги. Если загрузка прошивки на EP не требуется, пропустите первый пункт.

1. RC загружает прошивку на EP по PCIe.

Шаг 1. Скорость последовательного порта EP равна 1500000 (для RC также 1500000). После подключения постоянно выводится следующий журнал: канал PCIe установлен, EP ожидает прошивку от RC.

Шаг 2. Выполните на RC `./pcie_download_test_rc 0 ./uboot.img ./boot.img`. DMA переносит прошивку в заданную область памяти EP, затем команда запуска инициирует загрузку из DDR. EP выводит обычный журнал и входит в систему. При ошибке приложения RC см. examples/pcie_download_test/README.

```text
while true;
do
    cd /
    pcie_video_test_ep 1
done &
```

#### 3.2.2 Windows RC

Поставляемый драйвер Windows RC поддерживает только системы ниже Windows 10 2004. Для более новых систем требуется самостоятельно подготовить среду сборки и собрать драйвер. См. раздел построения среды драйвера Windows, прежде всего версию системы и отключение проверки подписи драйверов. После подготовки вставьте EP до включения PC. В диспетчере устройств найдите PCI-устройство: «Обновить драйвер» → «Выполнить поиск драйверов на этом компьютере» → каталог Win-Driver-RC → «Далее». После установки отображается Rockchip RC PCIE Driver for the rk35xx Accelerator Card. Запускайте тестовый инструмент от имени администратора. Показанный инструмент поддерживает загрузку прошивки, проверку скорости, декодирование видео и обнаружение объектов. При ошибках см. раздел устранения проблем.

## 4. Основы прикладной обработки карты EP

### 4.1 Принцип работы

Прикладная обработка EP передаёт исходные и обработанные процессором данные между сторонами по PCIe. Основные ресурсы:

RC:

- управление устройством EP через открытую стандартную библиотеку libpci;
- драйвер pcie-rkep выполняет отображение BAR (рекомендуется для управления), DMA (для блоков данных), обработку MSI, запуск ELBI и выделение DMA-памяти;
- пользовательский уровень активно опрашивает MSI для ускорения реакции, однако несколько согласований ограничивают работу в реальном времени;
- поддерживаются несколько процессов, например несколько pcie_speed_test.

EP:

- драйвер pcie_ep использует class id 0x1200 (Processing accelerators), отображает физическое входящее адресное пространство BAR, выполняет DMA, отправляет MSI и обрабатывает ELBI;
- активный опрос ELBI пользовательским уровнем ускоряет реакцию, но несколько согласований ограничивают работу в реальном времени;
- поддерживается многопоточность;
- VDEC, VENC, RGA, GPU и NPU доступны пользовательскому уровню через Rockit или RKNN.

## 5. Введение в Chips Connect

### 5.1 Принцип работы

Chips Connect — пользовательский комплект разработки на основе базовых функций EP. Он предоставляет интерфейсы передачи данных RC/EP в обоих направлениях и уведомления сообщениями, а также типовые прикладные сценарии.

| --- | --- | --- | --- |
| BAR0 | 0 | 4KB | Резерв EP: версия драйвера, состояние прерываний и т. д. |
|  | 12KB | 16KB | Конфигурация DEBUG |
|  | 16KB | 128KB | Состояние устройства EP |
|  | 128KB | 1M | Пользовательское |
|  | 1M | 4M | Обмен командами и управление buff |

#### 5.3.1 Инициализация

Выполняются две основные задачи:

1. Инициализация PCIe-устройства по VENDOR_ID, DEVICE_ID и адресу шины. Внутри libpci перечисляет PCIe-устройства системы и отображает BAR в приложение. Допускаются повторные вызовы rk_pcie_device_init с разными идентификаторами для инициализации устройств.

2. Вызов rk_pcie_task_create создаёт задачу и инициализирует память и состояние BUFF. Количество и размер буферов задаются struct pcie_task_attr_st. Конфигурация передаётся EP через BAR0; RC ожидает завершения инициализации EP.

EP получает сообщение создания задачи через rk_pcie_get_task_msg и запускает инициализацию, согласуя конфигурацию сторон. RC выбирает Hugepage/RKEP/RKDRM по параметрам сборки. Каждая карта EP создаёт на RC узел /dev/pcie-rkep* и получает отдельную большую непрерывную область памяти, если включена соответствующая настройка. EP после получения конфигурации инициализирует BUFF и выделяет физически непрерывную память через Hugepage/RKDRM. Данные BUFF обеих сторон размещаются в определённой области BAR0 для управления состоянием буферов.

```text
#define VENDOR_ID                   0x1d87
#define DEVICE_ID                   0x356a

struct pcie_dev_bus dev_bus;
int ret;
//获取系统匹配的PCI设备总线地址
ret = rk_pcie_get_pci_bus_addresses(VENDOR_ID, DEVICE_ID, &rc_ctx.dev_bus);
if (ret != 0) {
    printf("get pci bus address fail\n");
    return -1;
}

printf("ep dev max num : %d\n", rc_ctx.dev_bus.dev_max_num);
if (rc_ctx.dev_bus.dev_max_num == 0) {
    printf("no ep device, exit ... \n");
} else {
    rc_ctx.dev_attr.using_rc_dma = 0;
    rc_ctx.dev_attr.rc_dma_chn = 0;
    rc_ctx.dev_attr.enable_speed = 1;
    rc_ctx.dev_attr.vendor_id = VENDOR_ID;
    rc_ctx.dev_attr.device_id = DEVICE_ID;
    rc_ctx.dev_attr.use_dma_only_in_rc = 0;
    rc_ctx.dev_attr.mem_type = E_MEM_TYPE_HUGEPAGE;
    memcpy(rc_ctx.dev_attr.pci_bus_address, pci_bus_address, strlen(pci_bus_address));

    //选择第⼀个匹配设备初始化
    rc_ctx.rk_handle = rk_pcie_device_init(&rc_ctx.dev_attr);
    //获取EP设备模式
    rk_pcie_get_ep_mode(rc_ctx.rk_handle, &rc_ctx.devmode);
    printf("ep device init, dev mode: %d, submode: %d\n", rc_ctx.devmode.mode,
rc_ctx.devmode.submode);
}
```

#### 5.3.2 Передача данных

Передача состоит из трёх шагов:

1. Проверить наличие доступного BUFFER.

2. Получить BUFFER и записать в него данные.

3. Передать BUFFER другой стороне. Например, send_buff_num = 5 разрешает не более пяти передающих буферов. Отправитель получает свободный буфер и через struct pcie_buff_node узнаёт его физический и виртуальный адреса и размер. После прикладной обработки вызывается отправка. Внутри сначала очищается кэш буфера, чтобы физическая память содержала актуальные данные, затем DMA передаёт их другой стороне. Передаваемый размер node->size не должен превышать ёмкость BUFFER.

Отправленный буфер становится доступным снова только после освобождения получателем; иначе процесс блокируется. rk_pcie_get_buff пока не поддерживает блокирующий режим: ожидание реализуется циклом с sleep.

```text
struct pcie_buff_node *node = rk_pcie_get_buff(rk_handle, E_SEND);
if(node) {
    node->size = rk_pcie_get_buff_max_size(rk_handle, E_SEND);
    //操作buff 写⼊数据
    rk_pcie_send_buff(ctx->rk_handle, node);
} else {
    usleep(1000);
}
```

#### 5.3.4 Конфигурация BUFF

1. Передача RC → EP. В декодирующей карте RC отправляет исходные потоки EP; объём отдельного канала сравнительно мал. Размер BUFF можно задать как 4KB × число видеоканалов. Каждый поток передаёт 4KB за раз, чтобы обновлять данные при каждой передаче без излишне малых пакетов, расходующих полосу PCIe. Рекомендуется 3–5 циклически используемых буферов, минимум три. Если нужна дополнительная обработка, количество следует увеличить, иначе цикл остановится и скорость упадёт. При многопоточной передаче число буферов также можно увеличить.

2. Передача EP → RC. Обычно передаются большие декодированные данные: один кадр 1080p YUV422 занимает примерно 3MB. Один BUFF размером 3MB–6MB передаёт данные одного или двух каналов. Поскольку нужны несколько буферов для чередования, не следует чрезмерно увеличивать отдельный BUFF, занимая слишком много памяти.

### 5.4 Настройка памяти пользовательского уровня

RC и EP поддерживают несколько способов выделения памяти. Сторона RC:

1. Драйвер pcie-rkep выделяет память, SDK получает её отображением mmap. Включение: CONFIG_PCIE_FUNC_RKEP_USERPAGES=y (по умолчанию выключено). Размер изменяется макросом RKEP_USER_MEM_SIZE в pcie-rkep.c; по умолчанию 64M.

2. HugePages — рекомендуемый способ.

3. Драйвер DRM; необходимо заранее зарезервировать CMA в DTS. Размер DMA-памяти изменяется в arch/arm64/boot/dts/rockchip/rk3588-linux.dtsi:

```text
@@ -71,7 +71,7 @@ reserved-memory {
cma {
    compatible = "shared-dma-pool";
    reusable;
    reg = <0x0 0x50000000 0x0 0x10000000>; //从地址0x50000000开始256MB⼤⼩
    linux,cma-default;
};
```

4. Dummy: пользователь управляет буфером данных, а инфраструктура управляет только узлом чередования и не выделяет сам буфер. Сейчас поддерживается только Windows.

Сторона EP:

1. Драйвер DRM с предварительным резервированием CMA в DTS. Размер DMA-памяти изменяется в arch/arm64/boot/dts/rockchip/rk3588-linux.dtsi:

```text
@@ -71,7 +71,7 @@ reserved-memory {
cma {
    compatible = "shared-dma-pool";
    reusable;
    reg = <0x0 0x50000000 0x0 0x10000000>; //从地址0x50000000开始256MB⼤⼩
    linux,cma-default;
};
```

2. HugePages — рекомендуемый способ. Метод задаётся атрибутом при инициализации Task:

- RC: E_MEM_TYPE_HUGEPAGE / E_MEM_TYPE_RKDRM / E_MEM_TYPE_RKEP.
- EP: E_MEM_TYPE_HUGEPAGE / E_MEM_TYPE_RKDRM.

HugePages требует настройки системы; см. раздел HugePage.

### 5.5 Преимущества пользовательского драйвера

Перенос прикладного драйвера PCIe в пользовательский уровень упрощает использование и оптимизирует производительность.

Использование:

- Основа на PCIe-драйвере облегчает перенос между платформами.
- Прямое объединение с приложением позволяет вызывать rockit от RK или сторонние интерфейсы gstreamer.

В сравнении с драйвером интерфейса ядра:

- опрос вместо прерываний снижает расходы переключения режима CPU при частых прерываниях;
- уменьшаются переходы ядро/пользовательское пространство;
- рекомендуется привязка к CPU для уменьшения межъядерного планирования;
- устраняется копирование ядро/пользовательское пространство, обеспечивая zero-copy;
- Huge Page снижает промахи кэша TLB.

### 5.6 Несколько независимых приложений пользовательского уровня

Основа приложений RK chips_connect — Task:

- задачи независимы;
- сообщения пользователей RC независимы, RC Task поддерживает несколько процессов;
- сообщения пользователей EP управляются совместно, EP Task не поддерживает несколько процессов;
- внутри Task поддерживается многопоточность;
- Task ID выдаются в порядке запросов, конкретный ID задать нельзя.

В стандартном примере приложение не привязано к Task и другим ресурсам, поэтому независимые приложения параллельно не работают. Рекомендуется расширение через пользовательские сообщения с идентификатором приложения и принадлежностью Task. Пример для RK RT-Thread chips_connect:

1. Определите правила пользовательских сообщений и добавьте управление приложениями:

```text
struct task_user_cmd_st {
    unsigned int app_id;
    unsigned int cmd;
    unsigned char data[4];
};
```

2. EP регистрирует приложение с уникальным app_id.

3. RC отправляет сообщения с уникальным app_id.

4. Основная программа EP вызывает обработчик сообщения приложения по app_id.

5. Приложение EP обрабатывает сообщения, включая создание и освобождение Task.

## 6. Конфигурация Chips Connect

### 6.1 Пользовательский драйвер карты EP

Это функциональный драйвер EP на стороне RC, включающий модули ядра и пользовательские приложения.

#### 6.1.1 Режим Using-RC-DMA

Режим работает только при подключении EP к RK RC и позволяет максимально использовать полосу PCIe. По умолчанию используется лишь DMA EP. В Using-RC-DMA при записи EP → RC используется DMA EP, а при записи RC → EP — DMA RC, без взаимного вмешательства. DMA RC может передавать только в физические области, отображённые во входящий BAR, поэтому для него выделяется BAR2. По умолчанию размер 64M; он меняется DTS на EP. Эта память используется только при записи RC → EP и должна быть не меньше send_buff_size, задаваемого при инициализации.

Для включения не требуется менять драйверы RC/EP: достаточно настроить параметры инициализации приложения RC.

```text
dev_attr.using_rc_dma = 1; //使⽤RC DMA
dev_attr.rc_dma_chn = 1; //通道1，⽀持0/1
```

После включения приложение RC выводит следующий журнал:

```text
rk pcie version: v2.0.0 - 202300927
using rc dma: 1, chn: 1   //使能RC DMA，通道1
open rkrmd: /dev/pcie-rkep-0000:01:00.0 Success.
```

При создании Task приложение EP выводит следующий журнал:

```text
task create id: 1
using rc dma: 1
```

Рекомендуемая конфигурация:

- Один EP: включить using_rc_dma и выбрать канал 0.
- Несколько EP: отключить using_rc_dma и использовать DMA каждого EP, чтобы скорости карт оставались примерно равными.

## 7. Типовые сценарии Chips Connect

### 7.1 Карта ускорения видео EP

Карта передаёт видеопоток RC по PCIe на EP для декодирования и обработки, затем возвращает результат основной микросхеме для отображения. Основной поток обработки показан ниже.

![Технический рисунок оригинала, стр. 29](/docs/rockchip-pcie-ep-standard-card/assets/en-p029-figure-01.png)

*Технический рисунок оригинала, стр. 29*

Отправитель получает данные видеопотока, копирует их в подготовленный send stream buffer и через PCIe DMA передаёт в recv stream buffer противоположной стороны. Там поток извлекается и через VDEC поступает в VPSS. VPSS выдаёт два потока: один идёт в GPU для композиции, другой — в RKNN. Результат композиции копируется в подготовленный send stream buffer и через PCIe DMA передаётся в recv stream buffer другой стороны. Получатель извлекает данные и передаёт их модулю VO для отображения. SDK реализует буферы отправителя и получателя; достаточно настроить параметры при инициализации, сосредоточившись на прикладной обработке.

└── patch*                        # 补丁⽬录

Основные каталоги:

core/framework реализует общие для RC/EP функции: управление памятью, журналирование, linked_list, DMA, PCIe CONFIG и другие компоненты.

- framework/core/pcie: передача DMA и взаимодействие с конфигурацией DMA микросхемы.
- framework/core/mem: выделение и освобождение памяти при разных настройках.
- framework/osal: инкапсуляция интерфейсов ОС, скрывающая различия ОС от верхнего уровня.
- framework/base: базовые структуры, включая списки и очереди.

core/component инкапсулирует интерфейсы RC/EP, управление buf, сообщения и передачу данных, предоставляя API без вызовов через ОС. Три части:

- ep_pcie: управление buf, уведомления и передача на стороне EP.
- rc_pcie: те же функции для RC.
- cc_pcie_type.h и cc_cmp_pcie_type.h: единые структуры и типы данных для обмена RC/EP.

core/api инкапсулирует пользовательские интерфейсы различных систем. Оригинал называет четыре части, но перечисляет три:

- ep: RK EP нужен только arm; обёртка component/ep_pcie без дополнительной логики.
- rc/windows: реализация в форме драйвера с ioctl для пользователя.
- rc/other: другим системам драйверная форма не требуется; обёртка component/rc_pcie без дополнительной логики.

build: сборка SDK для Linux, Android и Windows.

docs: документация стандартной платы EP.

examples: тестовые примеры, описание и инструкции; см. README соответствующего каталога.

images: прошивки и примеры для непосредственной базовой проверки.

patch*: патчи SDK для Linux и Android; инструкции в patch*/README.

Холодная загрузка PC: выключить питание, включить питание, нажать POWER.

Пробуждение:

- RK RC: вход и выход из сна кнопкой POWER.
- Ubuntu: в настольной версии через интерфейс; остальные варианты требуют уточнения.

### 8.8 Совместимость: сброс EP и повторное перечисление RC

Цель: устойчивость при отдельном сбросе EP — remove/rescan PCIe, восстановление связи и нормальная работа приложения. Проверять после успешного завершения предыдущих функциональных тестов. Соберите examples/pcie_auto_test и подготовьте среду по examples/pcie_auto_test/README.md.

Для устройства 0 выполните на RC `./pcie_auto_test_rc 2 0` и `./pcie_auto_test_rc 3 0` для Remove и Rescan. Для проверки восстановления связи и приложения выполните `./pcie_auto_test_rc 0 0` — проверку стабильности API устройства 0.

## 9. Устранение проблем Chips Connect

### 9.1 Ошибка mmap failed, Operation not permitted при инициализации PCIe на x86 RC

```text
root@rk:/home/rc-sample# ./pcie_test 10240
resource path = /sys/bus/pci/devices/0000:01:00.0/enable
resource path = /sys/bus/pci/devices/0000:01:00.0/resource0
mmap failed, ret = 0, Operation not permitted
ep dev num : 1
Segmentation fault (core dumped)
```

Ответ оригинала: начиная с Ubuntu 20.04 используется kernel lockdown. Включённый Secure Boot в BIOS активирует lockdown и приводит к ошибке mmap. Оригинал предлагает отключить Secure Boot в BIOS. Это изменение защиты системы, а не выполненная здесь операция; применимость необходимо проверить для конкретной системы.

### 9.2 Настройка HugePage

RK поддерживает Hugepage 2M, 32M и 1GB; другие платформы зависят от системы. Размер одной Hugepage должен быть больше отдельного передающего и принимающего буфера SDK, а число страниц — достаточным для всех BUFF. Пример: пять передающих буферов по 4M и пять принимающих по 8M. 2M недостаточно, минимальная настройка — 32M.

Страницы отправки: (int) (5 / (32M / 4M)) + 1 = 1.
Страницы приёма: (int) (5 / (32M / 8M)) + 1 = 2.
Итого default_hugepagesz=32M, hugepagesz=32M, hugepages=3.

#### 9.2.1 Платформа X86

Проверьте Hugepagesize.

```text
rk@debian:~$ cat /proc/meminfo | grep Huge
HugePages_Total:       2
HugePages_Free:        2
HugePages_Rsvd:        0
HugePages_Surp:        0
Hugepagesize:    2048 kB
Hugetlb:         4096 kB
```

Измените размер на 1GB.

Измените cmdline: в /etc/default/grub добавьте default_hugepagesz=1G.

```text
GRUB_CMDLINE_LINUX_DEFAULT="quiet default_hugepagesz=1G hugepagesz=1G hugepages=1"
GRUB_CMDLINE_LINUX=""
```

Сгенерируйте конфигурацию.

```text
/usr/sbin/grub-mkconfig -o /boot/grub/grub.cfg
```

Перезапустите устройство: reboot или systemctl poweroff. Проверьте размер и количество: cat /proc/meminfo \| grep Hugepagesize.

```text
rk@debian:~$ cat /proc/meminfo | grep Huge
HugePages_Total:       1
HugePages_Free:        1
HugePages_Rsvd:        0
HugePages_Surp:        0
Hugepagesize:    1048576 kB
Hugetlb:         1048576 kB
```

### 9.3 Ошибка ядра или Bus error при доступе к user cmd или ep info после получения области через API

Две основные причины:

1. Использование memset или memcpy для этой области памяти.

2. Уровень оптимизации приложения выше -O1. В первом случае удалите memset/memcpy и используйте цикл for.

Во втором случае снизьте оптимизацию или добавьте -fno-tree-loop-optimize для отключения оптимизации циклов.

### 9.4 Среда сборки драйвера Windows

Среда разработки и проверки оригинала: Windows 10 2004, WDK 10.0.19041.685.

1. Подтвердите версию системы.

Откройте свойства компьютера или Win+R → winver. Обратите внимание на сборку 19042.1052, указанную в оригинале.

```text
版本                Windows 10 专业版
版本号              20H2
安装⽇期            2021/6/5
操作系统内部版本     19042.1052
```

2. Установите VS2019 и WDK, используя инструкции по их установке.

3. Оригинал перечисляет три способа отключения проверки подписи драйверов:

- Дополнительные параметры загрузки после перезапуска (обычно F8): выбрать отключение обязательной проверки подписи, если такой пункт доступен.
- Командная строка администратора: bcdedit /set testsigning on. Оригинал называет это временным отключением.
- Локальная групповая политика для Windows Pro и выше: gpedit.msc → Конфигурация компьютера → Административные шаблоны → Система → Установка драйверов; проверить разрешение установки неподписанных драйверов.

После перезапуска надпись Test Mode в правом нижнем углу указана как признак отключения. Согласно оригиналу, иначе драйвер не устанавливается. Эти изменения защиты здесь не выполнялись; Test Mode и отключение проверки подписей не следует автоматически считать тождественными.

4. Откройте build/windows/rk_projects/rk_projects.sln. Проект rc_pcie содержит драйвер. Из-за устаревания части API после Windows 10 2004 используются четыре конфигурации, описанные в оригинале:

- Debug_eq_win10_2004: Debug, системы выше Windows 10 2004.
- Debug_less_win10_2004: Debug, системы не выше Windows 10 2004.
- Release_eq_win10_2004: Release, системы выше Windows 10 2004.
- Release_less_win10_2004: Release, системы не выше Windows 10 2004.

examples — тестовый проект с Debug и Release. Результаты драйвера и тестов сохраняются в build/windows/rk_projects/x64.
